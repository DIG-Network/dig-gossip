# CON-005: Per-Connection Rate Limiting

> **Authoritative requirement:** [NORMATIVE.md](../NORMATIVE.md)
> **Verification:** [VERIFICATION.md](../VERIFICATION.md)
> **Tracking:** [TRACKING.yaml](../TRACKING.yaml)
> **Spec reference:** [SPEC.md - Section 5.3](../../../resources/SPEC.md)

## Summary

Rate limiting uses `chia-sdk-client::RateLimiter` with `V2_RATE_LIMITS`. Outbound rate limiting is built into `Peer::send_raw()` (it loops with 1-second sleep until the rate limit clears). Each inbound connection must have its own separate `RateLimiter` instance to enforce per-connection message frequency and size limits. DIG extension message types (200+ range) must be added to the rate limit configuration.

## Specification

### Outbound Rate Limiting (Built-in)

Outbound rate limiting is handled internally by `chia-sdk-client::Peer::send_raw()`. No additional implementation is needed for outbound:

```rust
// Peer::send_raw() internally enforces rate limits.
// It loops with a 1-second sleep until the rate limit window clears.
// This is provided by chia-sdk-client — we do NOT reimplement.
```

### Inbound Rate Limiting (Per-Connection)

Each inbound connection MUST have its own admission gate, holding both bounds behind one lock:

```rust
use dig_gossip::InboundRateLimiter;

// Create a separate gate for each inbound connection. It composes:
//   - chia_sdk_client::RateLimiter over V2_RATE_LIMITS, keyed by ProtocolMessageTypes
//   - DigRateLimiter over dig_extension_rate_limits_map(), keyed by the raw opcode byte
// Both use incoming = true and the same 60-second absolute window.
let inbound_limiter = InboundRateLimiter::new(config.peer_options.rate_limit_factor);
```

The DIG bound is keyed by the **raw opcode byte**, never by `ProtocolMessageTypes`. That is
deliberate and it is what lets a single table bound an opcode that is a Chia enum variant (221/222)
and one that is not (200-219) identically.

### DIG Extension Rate Limits

DIG-specific message types (200+ range) MUST be added to the rate limits configuration. The base `V2_RATE_LIMITS` covers standard Chia protocol messages; DIG extensions need additional entries:

```rust
use dig_gossip::RateLimit;

/// Extend V2_RATE_LIMITS with DIG-specific message type rate limits.
fn create_dig_rate_limits() -> RateLimits {
    let mut limits = V2_RATE_LIMITS.clone();

    // DIG extension message types (DigMessageType enum, 200+ range)
    // NewAttestation = 200
    limits.insert(200, RateLimit {
        frequency: 100,     // max per minute
        max_size: 4096,     // max message size in bytes
    });
    // NewCheckpointProposal = 201
    limits.insert(201, RateLimit {
        frequency: 10,
        max_size: 8192,
    });
    // NewCheckpointSignature = 202
    limits.insert(202, RateLimit {
        frequency: 100,
        max_size: 4096,
    });
    // RequestCheckpointSignatures = 203
    limits.insert(203, RateLimit {
        frequency: 10,
        max_size: 1024,
    });
    // RespondCheckpointSignatures = 204
    limits.insert(204, RateLimit {
        frequency: 10,
        max_size: 65536,
    });
    // RequestStatus = 205
    limits.insert(205, RateLimit {
        frequency: 10,
        max_size: 1024,
    });
    // RespondStatus = 206
    limits.insert(206, RateLimit {
        frequency: 10,
        max_size: 8192,
    });
    // NewCheckpointSubmission = 207
    limits.insert(207, RateLimit {
        frequency: 10,
        max_size: 65536,
    });
    // ValidatorAnnounce = 208
    limits.insert(208, RateLimit {
        frequency: 10,
        max_size: 4096,
    });

    // 220-band public broadcasts (ProtocolMessageTypes variants in the vendored fork, keyed
    // by their raw opcode in the same u8 -> RateLimit table as every other DIG row).
    // StoreMelted = 221 — fixed-size, infrequent public broadcast (#1316).
    limits.insert(221, RateLimit {
        frequency: 10,
        max_size: 4096,
    });
    // HoldingsAnnounce = 222 — signed, periodic public-discovery broadcast (#1720). Sized larger
    // than 221: max_size 131072 fits a full legit MAX_CHANGES (256) re-announce (~79 KiB), and
    // frequency 20 bounds the post-decode P-256 verify a hostile peer can force (vs the loose
    // 100-frame / 1 MiB default_settings it would otherwise fall through to).
    limits.insert(222, RateLimit {
        frequency: 20,
        max_size: 131072,
    });

    limits
}
```

**Opcode 220 (`DigMessage`, directed envelope) — base-bounded by design (accepted).**
Unlike the 221/222 public-flood broadcasts, opcode 220 carries a *directed* (unicast) dig-message envelope as opaque bytes; dig-gossip is pure transport and never opens, decodes, or verifies the envelope. Opcode 220 therefore has NO dedicated DIG rate-limit row and is deliberately bounded only by the Chia `default_settings` base limit — 100 frames/min, 1 MiB/frame, 100 MiB cumulative per connection — applied FIRST and unconditionally by `RateLimiter::handle_message` inside `InboundRateLimiter::allows`. This bound is REAL and non-fail-open: the fail-open `DigRateLimiter::check` runs only afterward and can add, never loosen, a restriction.

This is a conscious classification (`BASE_BOUND_ONLY_BAND_OPCODES`), asserted by the `every_220_band_opcode_is_classified` completeness guard. A tighter dedicated row is intentionally NOT added because (a) dig-gossip performs no per-frame crypto on a 220 frame (the envelope is opaque), so the per-frame cost the base bound already caps is only buffering + service broadcast; and (b) opcode 220 is the directed-message STREAMING transport (`StreamFrame` OPEN/DATA/CLOSE ride inside the opaque payload), so legitimate transfers fragment into many 220 frames and require high per-connection frame cadence — a tighter row would clip legitimate streaming while adding no security benefit against any abuse the base per-connection bound does not already cover.

**Inner `DigMessageType` limiting is out of scope for dig-gossip** and deferred to the recipient (dig-node), which alone decrypts the envelope and dispatches the inner type post-decrypt (cf. the per-origin churn limit). Any per-subtype ingress limiting is recipient-side defense-in-depth layered on top of this transport bound.

#### 220-band enforcement on the live gate (NORMATIVE, #1316 / #1720)

Opcodes `StoreMelted` = 221 (#1316) and `HoldingsAnnounce` = 222 (#1720) ARE
`chia_protocol::ProtocolMessageTypes` variants, so they arrive on the live wire as ordinary Chia
`Message` values — but their rate-limit rows live in the DIG table (`dig_extension_rate_limits_map`),
which `RateLimiter::handle_message` does NOT read (it consults only `default_settings`/`tx`/`other`).
Because these opcodes have no `tx`/`other` row, `handle_message` alone falls them through to the
loose `default_settings` (100 frames/min, 1 MiB), leaving their deliberate DIG bounds a no-op
on the live path.

Therefore the live inbound forwarders MUST run the combined admission gate
(`connection::inbound_limits::InboundRateLimiter::allows`), which — behind the single per-connection
mutex — requires BOTH `handle_message` AND, for any frame whose opcode is `>= 220`,
`DigRateLimiter::check(opcode, len)` to pass. Frames below opcode 220 are decided by `handle_message`
alone (unchanged). This is what makes the 221/222 rows enforced on the live wire; they MUST NOT be
treated as a "future ingress path" — they bind today.

## Inbound Message Checking

Every inbound message MUST be checked against the per-connection rate limiter before processing:

```rust
async fn handle_inbound_message(
    message: &Message,
    limiter: &mut InboundRateLimiter,
    peer_connection: &mut PeerConnection,
) -> Result<(), GossipError> {
    // Check both bounds for this message
    if !limiter.allows(message) {
        // Rate limit exceeded — apply penalty
        peer_connection.reputation.penalty_points += PenaltyReason::RateLimitExceeded.points();
        return Err(GossipError::ClientError(
            ClientError::RateLimitExceeded
        ));
    }

    // Process message...
    Ok(())
}
```

## Acceptance Criteria

- [ ] Each inbound connection has its own `InboundRateLimiter` instance
- [ ] Both halves are initialized with `incoming = true` for inbound connections
- [ ] `V2_RATE_LIMITS` is used as the base rate limit configuration
- [ ] DIG extension message types (200-208) are added with appropriate frequency and size limits
- [ ] Every inbound message is checked against the rate limiter before processing
- [ ] Rate limit violations apply a `RateLimitExceeded` penalty to the peer's reputation
- [ ] Outbound rate limiting is delegated to `Peer::send_raw()` (no custom implementation)
- [ ] Rate limiter uses the configured `rate_limit_factor` from `PeerOptions`
- [ ] Rate limit window is 60 seconds (reset_seconds)

## Implementation Notes

- Primary files: `src/connection/mod.rs` (rate limiter creation and checking)
- Dependencies: `chia-sdk-client` (RateLimiter, RateLimits, RateLimit, V2_RATE_LIMITS); the DIG per-opcode bound is dig-gossip's own `DigRateLimiter` (dig_ecosystem#2228)
- Edge cases:
  - `rate_limit_factor` of 0 effectively disables rate limiting (useful for testing)
  - DIG message types must not collide with existing Chia `ProtocolMessageTypes` (200+ range is safe)
  - Rate limiter state is per-connection and not shared between connections
  - If a peer repeatedly exceeds rate limits, the accumulated `RateLimitExceeded` penalties will trigger a ban (see CON-007)
  - `InboundRateLimiter::allows()` returns false if either bound is exceeded; it does not block
